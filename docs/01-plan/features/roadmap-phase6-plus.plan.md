## 1. 현재 제품 완성도 평가

### Phase 1~5 달성 현황

| 구분 | 내용 | 완성도 |
|------|------|--------|
| 콘텐츠 생성 | 7단계 파이프라인 (리서치→품질검증) | 완성 |
| 승인 게이트 | 텔레그램 승인 + 반려 | 완성 |
| 발행 | 네이버 + 티스토리 자동 발행 | 완성 |
| 데이터 수집 | RSS 7개 소스 자동 수집 + 큐레이션 | 완성 |
| 자동화 | APScheduler 기반 전자동 일일 파이프라인 | 완성 |

### 강점
- **핵심 루프 완성**: 수집 → 생성 → 승인 → 발행의 전체 사이클이 작동
- **플랫폼 차별화**: 네이버(설민석 스타일) / 티스토리(전문 리뷰어 스타일) 분리 전략
- **비용 최적화**: 배치 처리, 제목+요약만 번역하는 효율적 Claude API 사용
- **품질 게이트**: 큐레이션 7점 임계값 + 텔레그램 최종 승인

### 현재 한계 (개선 필요 영역)
- **데이터 소스 한계**: RSS 7개만 활성화. 웹스크래핑/API/트렌드 소스 미구현 (15개 중 7개)
- **운영 안정성**: 프로세스 재시작 자동화 없음 (systemd/pm2 미설정)
- **가시성 부재**: 성과 데이터(조회수, 방문자)를 수집·분석하는 기능 없음
- **모니터링 부재**: 파이프라인 실패 알림은 있으나 대시보드 없음
- **콘텐츠 다양성 제한**: 글 유형(content_types)이 고정적, 트렌드 키워드 활용 안 됨

### 종합 완성도 평가
**MVP 완성 단계 (70%)** — 자동화 파이프라인의 핵심 기능은 모두 구현됨.
본격 운영 안정화와 데이터 소스 확장을 통해 실용적 수익화 단계(90%)에 도달 가능.

## 2. Phase 별 우선순위 및 범위 제안

### Phase 6: 운영 안정화 + 인프라 (Must)

**비즈니스 가치**: 현재 파이프라인이 실서버에서 중단 없이 돌아가야 수익화 가능. 안정성 없이는 이후 확장이 무의미.

**예상 기간**: 1~2주

#### In Scope

**6-1. 배포 인프라**
- `systemd` 서비스 파일 작성 (`ai-blog-automation.service`)
  - 서버 재부팅 시 자동 시작 (`WantedBy=multi-user.target`)
  - 비정상 종료 시 자동 재시작 (`Restart=on-failure`)
- Docker Compose 운영 프로필 (`docker-compose.prod.yml`)
  - app + Redis + (선택) PostgreSQL 컨테이너
  - 볼륨 마운트: `data/`, `logs/`
- VPS 배포 스크립트 (`scripts/deploy.sh`)
  - git pull → docker compose up --build → health check

**6-2. 헬스체크 + 자동 복구**
- `utils/health_checker.py` — 핵심 의존성 상태 확인
  - Claude API 응답 여부
  - DB 연결 상태
  - Telegram Bot 연결 상태
- 시작 시 헬스체크 → 실패 시 텔레그램 알림 + 프로세스 종료
- `cli.py health` 커맨드 추가

**6-3. 로그 관리**
- 로그 로테이션 설정 (`logrotate` 또는 Python `RotatingFileHandler`)
- 에러 로그 별도 파일 분리 (`logs/error.log`)
- 30일 이상 로그 자동 삭제

**6-4. DB 마이그레이션 전략**
- Alembic 도입 (SQLAlchemy 마이그레이션)
- SQLite → PostgreSQL 전환 가이드 문서
- `cli.py db migrate` 커맨드

#### Out of Scope
- 다중 인스턴스 / 분산 스케줄링
- 클라우드 관리형 DB (RDS 등)

### Phase 7: 데이터 소스 확장 (Should)

**비즈니스 가치**: 현재 RSS 7개로는 주제 다양성 한계. 웹스크래핑 + API 소스 추가로 콘텐츠 발굴 범위를 2배 이상 확장.

**예상 기간**: 2~3주

#### In Scope

**7-1. 웹 스크래핑 소스 (4개)**
- `collectors/web_scraper.py` — Playwright 기반 범용 스크래퍼
- 대상: Anthropic News, Google DeepMind Blog, Meta AI Blog, Product Hunt AI
- 셀렉터 기반 추출 → `config/scrapers.yaml`에 설정화
- 사이트 변경 감지 알림 (구조 변경 시 텔레그램 알림)

**7-2. API 소스 (2개)**
- `collectors/reddit_collector.py` — PRAW 라이브러리
  - r/ChatGPT, r/artificial, r/MachineLearning hot/top(daily)
  - Rate limit 관리 (분당 60회)
- `collectors/hn_collector.py` — Hacker News Algolia API
  - AI/ML 키워드 필터링, 포인트 50+ 게시글

**7-3. 트렌드 소스 (2개)**
- `collectors/trend_collector.py`
  - 네이버 데이터랩 API (검색어 트렌드)
  - pytrends (Google Trends KR)
- 매일 06:00 수집 (1회/일)
- 수집된 트렌드 키워드를 큐레이션 에이전트에 컨텍스트로 전달

**7-4. 소스 통합 오케스트레이터 업그레이드**
- `collectors/collector_orchestrator.py` — 15개 소스 통합 관리
- 소스별 실패 격리 (1개 실패해도 나머지 계속)
- 수집 결과 소스별 통계 로깅

#### Out of Scope
- X(Twitter) API (비용 문제)
- YouTube 채널 스크래핑
- arxiv 논문 수집

### Phase 8: 성과 분석 + 피드백 루프 (Should)

**비즈니스 가치**: 어떤 주제/글 유형이 실제로 조회수를 얻는지 데이터 없이는 최적화 불가능. 피드백 루프가 없으면 품질이 정체됨.

**예상 기간**: 2~3주

#### In Scope

**8-1. 성과 데이터 수집**
- `analytics/naver_analytics.py` — 네이버 블로그 통계 API 또는 스크래핑
  - 게시글별 조회수, 댓글 수, 공감 수
- `analytics/tistory_analytics.py` — 티스토리 통계 API
  - 게시글별 방문자, 유입 키워드
- 수집 주기: 매일 22:00 (발행 후 익일 데이터)

**8-2. 성과 DB 모델**
- `PostMetrics` 테이블: post_id, platform, views, comments, likes, collected_at
- `TopicPerformance` 뷰: 주제 유형별 평균 성과

**8-3. 큐레이션 피드백**
- 성과 좋은 글의 주제/유형/키워드 패턴 분석
- 큐레이션 에이전트 프롬프트에 "과거 성과 데이터" 컨텍스트 추가
- `cli.py analytics` — 성과 리포트 출력 (최근 30일)

**8-4. 일일 요약 알림 고도화**
- 기존: 수집/생성/발행 수만 알림
- 추가: 전날 발행글 조회수, 누적 통계 (총 발행 수, 총 조회수)

#### Out of Scope
- 광고 수익 자동 계산
- 경쟁 블로그 분석

### Phase 9: 웹 대시보드 (Could)

**비즈니스 가치**: 운영 현황을 텔레그램 메시지 대신 브라우저에서 확인. 비개발자도 운영 가능한 수준의 UX 제공.

**예상 기간**: 3~4주

#### In Scope

**9-1. 백엔드 API**
- FastAPI 기반 REST API (`api/` 폴더)
- 엔드포인트:
  - `GET /api/topics` — 큐레이션된 주제 목록
  - `GET /api/posts` — 생성된 글 목록 + 상태
  - `GET /api/analytics` — 성과 요약
  - `POST /api/generate` — 수동 글 생성 트리거
  - `POST /api/approve/{post_id}` — 웹에서 승인
- JWT 기반 인증 (단일 사용자)

**9-2. 프론트엔드 (경량)**
- 별도 프레임워크 없이 HTMX + Alpine.js + Tailwind CSS
  - 이유: 1인 개발자에게 React/Vue는 과도한 복잡도
- 페이지:
  - 대시보드 (오늘의 현황 요약)
  - 주제 큐레이션 목록 (점수 + 선택/제외)
  - 글 목록 (발행 상태, 조회수)
  - 스케줄 상태 (다음 실행 시간)

**9-3. 텔레그램 승인 병행 유지**
- 웹 승인과 텔레그램 승인 모두 지원
- 둘 중 먼저 처리된 것 우선

#### Out of Scope
- 모바일 앱
- 다중 사용자 / 팀 기능
- 실시간 WebSocket 알림 (Long polling으로 대체)

**비즈니스 가치**: 동일 파이프라인에서 더 높은 품질·다양성의 콘텐츠를 생성. SEO 경쟁력 강화.

**예상 기간**: 2~3주

#### In Scope

**10-1. 트렌드 키워드 기반 SEO 자동 최적화**
- 네이버 데이터랩 + Google Trends 키워드를 SEO 에이전트에 직접 반영
- 키워드 경쟁도 분석 (검색량 대비 블로그 수)
- 저경쟁 고검색량 키워드 자동 타겟팅

**10-2. 콘텐츠 시리즈 관리**
- 연관 주제 묶어 시리즈 발행 (예: "ChatGPT 완전 정복 1~5편")
- `ContentSeries` DB 모델 추가
- 시리즈 내 글 간 내부 링크 자동 삽입

**10-3. 유사도 모니터링 강화**
- 현재: 네이버/티스토리 간 유사도 55% 이하 유지
- 추가: 과거 발행글과의 유사도 체크 (중복 주제 방지)

**10-4. 썸네일 생성 자동화**
- 현재: 썸네일 설정만 있고 실제 생성 미구현
- DALL-E 3 또는 Stable Diffusion API 연동
- 주제 키워드 기반 프롬프트 자동 생성

#### Out of Scope
- 영상 콘텐츠 자동화
- 음성 콘텐츠 (팟캐스트)

## 4. 사용자 경험 개선 방향

### 현재 (CLI 기반)
```
사용자: python cli.py scheduler  (1회 실행 후 방치)
         → 텔레그램 메시지 확인 (모바일)
         → 텔레그램에서 승인/반려 버튼 클릭
         → 하루 1~2회 텔레그램 일일 요약 확인
```

### Phase 6 이후 (안정화)
```
사용자: systemd start ai-blog  (서버 재시작 시 자동 시작)
         → 동일 텔레그램 플로우
         → 추가: 서버 이상 시 자동 알림 수신
```

### Phase 8 이후 (성과 기반)
```
사용자: 텔레그램 일일 요약에 "어제 발행글 조회수 1,234" 포함
         → 성과 데이터 기반으로 주제 선택 패턴 개선
```

### Phase 9 이후 (웹 대시보드)
```
사용자: 브라우저에서 대시보드 접속
         → 큐레이션 주제 목록에서 원하는 주제 선택/제외
         → 텔레그램 대신 웹에서 승인 가능
         → 성과 그래프 시각화 확인
```

### UX 개선 핵심 원칙
1. **텔레그램 플로우 유지**: 모바일 편의성이 가장 높음. 대시보드는 보완이지 대체가 아님
2. **알림 정보 밀도**: 불필요한 알림은 피로도 증가. 핵심 지표만 포함
3. **수동 개입 최소화**: 승인 외 모든 작업은 자동화 유지

## 5. 운영 안정성 관점 필요 기능

### 5-1. 즉시 필요 (Phase 6)
| 기능 | 이유 | 구현 방법 |
|------|------|-----------|
| systemd 자동 재시작 | 서버 재부팅, 크래시 대응 | `Restart=on-failure` |
| 헬스체크 엔드포인트 | 외부 모니터링 연동 | `cli.py health` |
| 로그 로테이션 | 디스크 풀 방지 | logrotate 또는 Python |
| DB 백업 | 데이터 손실 방지 | 주 1회 SQLite 파일 복사 → S3 또는 로컬 |

### 5-2. 중기 필요 (Phase 7~8)
| 기능 | 이유 | 구현 방법 |
|------|------|-----------|
| 소스별 실패 격리 | 1개 소스 오류가 전체 중단 방지 | try-except per source + 텔레그램 알림 |
| API Rate Limit 관리 | Reddit API, 네이버 API 제한 준수 | 토큰 버킷 알고리즘 또는 asyncio.sleep |
| 스케줄 작업 Lock | 동시 실행 방지 | APScheduler `coalesce=True` + DB Lock |
| 비용 추적 대시보드 | Claude API 일일 비용 모니터링 | 기존 cost_tracker.py 확장 |

### 5-3. Phase 5 리스크 해소 타임라인
| 리스크 (Phase 5 문서) | 해소 Phase | 해소 방법 |
|--------------------|-----------|-----------|
| 프로세스 종료 시 스케줄 중단 | Phase 6 | systemd |
| 장기 실행 시 메모리 누수 | Phase 6 | 메모리 모니터링 추가 |
| 작업 충돌 (Lock) | Phase 7 | APScheduler coalesce + DB Lock |

## 6. 경쟁력 강화 차별화 기능 제안

### 6-1. 플랫폼 최적화 심화
현재 네이버/티스토리 스타일 차별화가 있으나, SEO 알고리즘 대응이 미흡.

- **네이버 VIEW 최적화**: 네이버 블로그 노출 알고리즘(C-Rank) 대응
  - 글 길이 최적화 (2,000~3,000자 권장)
  - 이미지 alt 텍스트 자동 최적화
  - 연관 태그 자동 생성 (네이버 인기 태그 참조)
- **티스토리 구글 SEO**: 구조화 데이터(JSON-LD) 자동 삽입
  - Article, BreadcrumbList 스키마

### 6-2. 한국 특화 맥락 추가
현재 해외 소스 기반 글에 "한국 맥락"을 추가하는 것이 핵심 차별화 요소.

- **국내 사례 자동 추가**: 큐레이션 에이전트가 국내 기업 활용 사례 검색 (ZDNet, AI타임스 교차 참조)
- **한국어 검색 최적화**: 동일 키워드의 한국어 변형 자동 생성 (예: "AI" → "인공지능", "에이AI")
- **계절/이슈 연동**: 국내 주요 이슈(AI 관련 정부 정책, 대기업 발표)와 콘텐츠 연결

### 6-3. 콘텐츠 재활용 전략
한 번 생성한 고성과 글을 최대한 활용.

- **업데이트 글 자동화**: 6개월 이상 지난 인기 글을 최신 정보로 업데이트 재발행
- **시리즈 연결**: 단발성 글을 시리즈로 묶어 체류 시간 증가
- **플랫폼 간 링크**: 네이버 글에서 티스토리 심화 글로 유도 (트래픽 교차)

### 6-4. 운영 차별화
- **주제 예약 기능**: 특정 날짜에 발행할 주제를 미리 큐에 넣어두기 (이슈 예측 발행)
- **발행 시간 최적화**: 플랫폼별 최적 발행 시간 데이터 수집 후 스케줄 자동 조정
- **카테고리 균형 강화**: 기존 `balance_rules.yaml` 실제 적용 (현재 정의만 있고 미구현)

## 7. 기술 부채 해소 시점 제안

### 현재 확인된 기술 부채

| 부채 항목 | 현황 | 해소 시점 | 해소 방법 |
|-----------|------|-----------|-----------|
| SQLite → PostgreSQL | SQLite로 개발 중 | Phase 6 배포 시점 | Alembic + Docker PostgreSQL |
| 썸네일 생성 미구현 | config만 있고 실제 생성 없음 | Phase 10 | DALL-E 3 API 연동 |
| `balance_rules.yaml` 미적용 | 파일만 존재 | Phase 7~8 | 큐레이션 에이전트에 균형 규칙 통합 |
| n8n 워크플로우 | 폴더 존재하나 활용 미확인 | Phase 9 또는 제거 | APScheduler로 대체하거나 정리 |
| 테스트 커버리지 | Phase별로 쌓이는 중 | Phase 8 완료 후 | 통합 테스트 + E2E 테스트 추가 |
| 프롬프트 버전 관리 | config/prompts에 있으나 Git 외 관리 없음 | Phase 8 | 프롬프트 성과 추적 테이블 추가 |

### 기술 부채 해소 원칙
1. **기능 확장과 병행**: 별도 "리팩터링 Sprint"보다 새 기능 추가 시 함께 해소
2. **SQLite 전환 시점**: VPS 이전(Phase 6) 직전이 가장 적합. 이후에는 데이터 마이그레이션 부담 증가
3. **n8n 정리 기준**: Phase 9 웹 대시보드 완성 후 n8n이 중복이면 제거, 가치 있으면 통합

## 8. 권장 실행 순서

```
현재 (Phase 5 완성)
    ↓
Phase 6: 운영 안정화 (1~2주) ← 최우선. 배포 없이는 실제 수익화 불가
    ↓
Phase 7: 데이터 소스 확장 (2~3주) ← 콘텐츠 발굴 다양화
    ↓
Phase 8: 성과 분석 (2~3주) ← 데이터 기반 개선 사이클 시작
    ↓ (선택적 병행)
Phase 9: 웹 대시보드   또는   Phase 10: 콘텐츠 지능화
(운영 편의성 우선)              (품질/SEO 우선)
```

### 의사결정 기준
- Phase 9를 먼저 선택하는 경우: 운영자가 비개발자이거나, 텔레그램 UX에 불편함이 있을 때
- Phase 10을 먼저 선택하는 경우: 발행 중인데 조회수가 낮을 때, SEO 개선이 시급할 때
